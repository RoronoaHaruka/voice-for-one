# 企微语音条

> © 2026 Raincove ♡ · Roronoa & Haruka · 文档 [CC BY-NC-SA 4.0](../LICENSE) · 代码 [PolyForm Noncommercial 1.0.0](../LICENSE-CODE)
>
> 把一句话说成企业微信的**原生语音条**：出现在个人微信会话里的那种语音泡泡，点开即播，长按可转文字。本篇是工艺侧的正典；企业微信整条桥接链路（回调、客服双入口、路由与受控发送工具）见 [wecom-companion-guide](https://github.com/RoronoaHaruka/wecom-companion-guide)。

## 先看结论

- 自建应用门与微信客服门都能发原生语音条：`msgtype=voice`。素材硬边界是 **AMR 格式、不超过 2MB、不超过 60 秒**，三条都是接口侧强制。
- 链路五步：一句话文本 → TTS → MP3/WAV → 8kHz 单声道 PCM → AMR-NB → `media/upload?type=voice` 拿 `media_id`，应用门走 `message/send`，客服门走 `kf/send_msg`。
- 语音条经微信插件进入个人微信后，显示为原生语音泡泡，正常可播可转文字。

```text
一句话文本
   │  TTS（key 只在服务器）
   ▼
MP3/WAV ─ ffmpeg 解码 → 8kHz 单声道 PCM ─ AMR-NB 逐帧编码 ─┐
                                                              ├─ media/upload?type=voice → media_id
      应用门 message/send(msgtype=voice)  ◄───────────────────┤
      客服门 kf/send_msg(msgtype=voice)   ◄───────────────────┘
```

## 格式这一关：AMR-NB

| 约束 | 值 |
|---|---|
| 容器与编码 | AMR（窄带 AMR-NB，8kHz 单声道），文件头 `#!AMR\n` |
| 大小 | ≤ 2MB |
| 时长 | ≤ 60 秒 |
| 素材有效期 | 临时素材三天过期，`media_id` 不可长存 |

多数发行版的 ffmpeg **解**得动 AMR 却**编**不出来（`libopencore_amrnb` 编码器没编译进去）。最稳的两步走：先用 ffmpeg 把任意音频解到 8kHz 单声道 s16le PCM，再调用 `libopencore-amrnb` 的 C 接口逐帧编码，一帧 160 个样本，12.2kbps（mode 7），开头写上 `#!AMR\n`。本仓库 [`../code/to_amr.py`](../code/to_amr.py) 就是这条链的独立实现。系统依赖两件（Debian 系包名）：

```bash
apt install ffmpeg libopencore-amrnb0
```

如果你的 ffmpeg 恰好带编码器，一条命令等价：

```bash
ffmpeg -i voice.mp3 -ar 8000 -ac 1 -c:a libopencore_amrnb voice.amr
```

## 发出去是电流声

语音条发送成功、手机上点开却只有滋啦滋啦的电流，几乎都是同一种病：文件过了服务器的关，却过不了手机端的解码器。`media/upload?type=voice` 这一关只看文件开头有没有 `#!AMR` 这几个字节，其他一概不查。实测四种文件：正常 AMR-NB 通过；`#!AMR-WB\n` 开头的宽带 AMR 通过；正确文件头后面接一段随机字节也通过；mp3 改后缀、没有文件头的裸帧则被 `301017` 当场拒绝。所以真正会带着「发送成功」走到手机里的坏文件只有两类：

- **AMR-WB（宽带、16kHz）**。微信与企微手机端只解窄带 AMR-NB，宽带帧塞进窄带解码器就是电流。ffmpeg 用了 `libvo_amrwbenc`、安卓录音选了 `AMR_WB`、在线转换默认给的 WB，都属此类。
- **文件头对、帧是坏的**。编码器吃到的 PCM 不是 8kHz 单声道 16bit 小端（喂了 float、喂了 16k/44.1k 没重采样、把 mp3 字节直接当 PCM），或者用的库输出的是裸帧、IF2 帧，而不是每帧带 ToC 字节的 `.amr` 存储格式。

上传之前在本机三步自查，比发出去再听省事得多：

```bash
head -c 9 voice.amr | xxd          # 应为 #!AMR 紧跟换行；看到 #!AMR-WB 即宽带
ffprobe voice.amr                  # 应为 amr_nb, 8000 Hz, mono
ffmpeg -i voice.amr check.wav      # 解回去自己听一遍，本机就是电流就别上传了
```

## 两扇门怎么发

上传与发送是固定两步：`media/upload?type=voice` 换 `media_id`，再按门发送。应用门 `message/send`，`msgtype=voice`；客服门 `kf/send_msg`，同样的 `msgtype`。注意客服门的语音与文本共用同一份**每轮五条回复额度**，发送侧应当占用同一份预算、并用稳定 `msgid` 接住网络重试；自建应用门没有会话条数额度，只有宽裕的接口频控。

受控发送工具的完整实现（收件人白名单、绑定客户校验、时长与字节上限、预算管理）是 wecom-companion-guide 的 [`voice_sender.py`](https://github.com/RoronoaHaruka/wecom-companion-guide/blob/main/code/voice_sender.py)，它长在那边的路由与队列体系上，桥接细节以那边为准。

## TTS 选型

选表现力强、支持表演标签的档位：呼吸、轻笑、耳语要能从台词里自己长出来。写台词与做场景的整套工艺见[番外 · 场景感语音](场景感语音.md)；做音色的两条路（voice clone 与文字描述生成）也在那篇里。做 voice clone 只有一条不可让步的规矩：**音源必须是你有权使用的**。

## 一段诚实的边界

这条语音链路属于企业微信自建应用与微信客服两扇官方门。至于各种逆向协议的「个人微信机器人」，其原生语音通道在 2026 年年中之后已被服务端封死：消息显示发送成功，对端永远收不到，且无任何报错。走正门，语音条今天依然到达。

## 验证清单

- [ ] 生成的 AMR 以 `#!AMR\n` 开头，8kHz 单声道，60 秒与 2MB 以内。
- [ ] 上传前 `ffprobe` 确认是 `amr_nb`（宽带 `amr_wb` 与坏帧都能通过上传、到手机上变电流声）。
- [ ] 应用门语音条在个人微信（微信插件）里显示为可点播的语音泡泡，长按可转文字。
- [ ] 客服门语音条到达，且五格回复预算相应减一。
- [ ] 超长文本在 TTS 调用**之前**就被拦下（先省下生成费）。
